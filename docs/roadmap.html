#2 · Flows in depth

Three front-doors, one drift-tolerant clock

A flow can start three ways, and everything it does is traceable back to which door it came through. Scheduling is deliberately not real cron — the laptop is sometimes off.

Manual one-off

Run now

A button in the UI, corral flow run <name> on the CLI, or "run the triage flow" in host chat. Same entrypoint, three doors — the trigger source is recorded on every run.

Scheduled pseudo-cron

Drift-tolerant clock

A ~1-minute tick reconciles each flow's last_run_at against its cadence. Machine was off for 3 days? A daily flow fires once on wake — never replays every missed day. Per-flow override.

Composition the hard part

Passing data step to step, with a UX that stays friendly

MCP prompt → create issue → start a sandclaude on that issue → open a PR. Each step's output threads into the next via {{steps.<key>.output}}. The schema is DAG-ready today; execution goes from linear to dependency-ordered.

already in place: auto_flows · auto_flow_steps (position, depends_on_json, input_map_json) · auto_runs history · linear runner. to build: trigger emission · scheduler · DAG execution · the builder UI.
#0 · Follow the thread

Everything is traceable

A chat turn asks Claude to triage. Claude calls a flow. The flow pulls from an MCP, opens an issue, and launches a sandbox. One trace, one tree — reconstructed from trace_id / span_id / parent_span_id on the log rows.

Independent tracks · interleave anytime

The standalone wins

These don't wait on the spine. #7 is small and high-value; #8 is a real cost saver; #6 is the flashiest demo. Each can slot in between the bigger phases.

#7 quick win

Named prompts

Save prompts by name and pick one when starting a project or working an issue — instead of custom, per-repo, or global only. Today prompts are a repo/global override catalog; this adds a real user-named library.

builds on: prompts_catalog · three-level override · claude_prompt actions.
#8 cost saver

Reusable data cache

Stop rebuilding DinD images and volume data every one-off. A named, snapshottable volume layer: copy-on-write clone for throwaway runs, update-in-place when a migration should persist the Postgres data.

builds on: DindVolumeName deterministic per-workspace volume — no snapshot/clone today.
#5 scoping

Per-repo skills & AGENT.md

Attach skills and an AGENT.md to specific repos so a sandbox checkout carries the right context and capabilities for that codebase.

builds on: repo-scoped config already threads into project start.
#6 the demo

Watch Claude work

A headed view: port-bind from DinD and stream it into an iframe. Watch a Playwright run drive a browser and take a screenshot, live. Needs a display (Xvfb + noVNC), a little more than raw port binding.

builds on: DinD port forwarding + firewall stream (SSE) already exist.
